# Claude Opus 4.7 编码最佳实践指南

> 面向 vue3-element-admin 这类中后台项目，结合 GitHub Copilot Chat (Agent 模式) + Claude Opus 4.7 的高质量使用方法。

---

## 一、核心心法：把 AI 当"高级实习生"而非"魔法师"

| 心态 | 说明 |
| --- | --- |
| **明确意图** | 不要让模型猜，写清楚"做什么、在哪里、约束是什么、验收标准" |
| **提供上下文** | 主动给文件路径、相关代码、设计稿、接口定义、字段示例 |
| **小步快跑** | 一次只让它做一件可验证的事，禁止"一次性把整个模块写完" |
| **看完再合** | 把 diff 当 PR Review；不要看都不看就 Accept |
| **会话即记忆** | 同一会话里持续微调；切换大任务时另开会话防止上下文污染 |

## 二、通用 Prompt 结构（强烈推荐套用）

```
【目标】一句话说清楚要干什么
【背景】为什么做、相关业务名词、所属模块
【范围】涉及哪些文件 / 目录（贴路径）
【约束】
  - 技术栈：Vue3 + TS + Element Plus + UnoCSS + Pinia
  - 必须复用：xxx 组件 / xxx composable
  - 禁止：引入新依赖 / 修改 xxx 文件
【参考】贴接口字段、Mock 数据、相似已存在页面路径
【验收】
  - 路由可访问 /xxx
  - 列表 / 表单 / 校验 / Mock 都通
  - tsc 无报错、eslint 通过
```

> 示例：
> 「在 `src/views/affairs/` 下新增"请假申请"页面，参考 `src/views/affairs/requirements/index.vue` 的写法，Mock 走 `mock/affairs.mock.ts`，字段见下方 JSON，验收：路由 `/affairs/leave` 可访问，表格 + 新增 + 编辑 + 删除均能跑通。」

## 三、典型场景操作手册

### 场景 1：新增一个 CRUD 页面

推荐拆分为 **4 个连续提问**，而不是一次说完：

1. **找参考**
   > "找一个项目里最接近 CRUD 列表页的现有页面，列出它的文件结构和依赖（路由、API、Mock、组件）。"

2. **生成 API + Mock**
   > "参考 `src/api/affairs/requirements.ts` 风格，为'请假申请'生成 API 与 Mock，字段如下：…"

3. **生成页面**
   > "基于上一步的 API，仿照 `requirements/index.vue` 实现页面；表格列：xxx；表单字段：xxx；必填项：xxx。"

4. **接路由 + 菜单**
   > "在 `mock/menu.mock.ts` 中插入菜单项，并确认路由懒加载路径正确。"

每一步结束后，亲自跑一遍 / 看一眼 diff，再进入下一步。

---

### 场景 2：修改已有功能

**黄金三步：定位 → 影响面 → 改动**

1. **定位**
   > "在仓库中找出所有使用 `xxxApi.getList` 的位置，并列出文件和行号。"

2. **影响面分析**
   > "我要把返回字段 `name` 改成 `fullName`，列出所有需要同步修改的地方，包括类型定义、模板、表头、搜索表单。"

3. **执行修改**
   > "按上一步清单依次修改，并保持其它逻辑不变。改完后告诉我哪些地方风险最高需要我重点回归。"

> ⚠️ 修改类任务最容易出问题的是**漏改**。一定要先让它列清单，再批量动手。

---

### 场景 3：修 Bug

```
【现象】点击保存后表格不刷新
【复现】xxx 页面 → 新增 → 填写 → 保存
【已知】Network 看到接口 200，data.code === 0
【期望】保存后自动刷新列表
【排查范围】src/views/xxx/，相关 composable
请先给出 3 个最可能的原因，不要急着改代码。
```

> 让模型**先诊断、后动手**。直接让它"修一下"往往会引入新 bug。

---

### 场景 4：重构 / 抽公共逻辑

- 先让它**只读不写**：列出重复代码段、给出抽象方案、对比利弊。
- 你拍板方案后，再让它执行。
- 重构后必须要求："保持外部行为完全不变，给我列出 before/after 的调用方式对比。"

## 四、上下文管理技巧

| 技巧 | 做法 |
| --- | --- |
| **贴路径优于贴代码** | 直接给 `src/views/xxx/index.vue`，让它自己读，比你粘贴一大段更准 |
| **贴关键片段** | 当涉及跨文件约定时，把类型定义 / 接口字段贴出来 |
| **使用 #file / #selection** | Copilot Chat 里用 `#` 引用，比口头描述精确 |
| **避免一次给十个文件** | 上下文越长越容易丢细节；用"分步走"代替"一锅烩" |
| **及时纠偏** | 发现它跑偏立刻打断："停，先不要动 xxx，只做 yyy" |
| **大任务开新会话** | 跨模块大改动，重启会话避免旧上下文干扰 |

## 五、代码质量护栏

让模型在产出代码时**默认遵守**以下规则（可写进 `copilot-instructions.md` 或每次 Prompt 末尾）：

```
- TypeScript 严格模式，禁止 any，未知类型用 unknown + 类型守卫
- 组件用 <script setup lang="ts">，props/emits 显式声明类型
- 样式优先 UnoCSS 原子类，复杂样式用 scoped scss
- 表格、表单、弹窗复用项目内现有组件（Pagination、DictSelect、CURD 等）
- API 统一放 src/api/<模块>/，Mock 同步更新 mock/<模块>.mock.ts
- 不要新增依赖，除非我明确同意
- 不要添加多余注释；只在"为什么"非显而易见时加一行
- 改动尽量小，不顺手重构无关代码
```

## 六、验收 Checklist（每次合并前过一遍）

- [ ] `pnpm type-check` / `tsc --noEmit` 无报错
- [ ] `pnpm lint` 通过
- [ ] 浏览器手动跑一遍主流程（新增 / 编辑 / 删除 / 搜索 / 分页）
- [ ] 控制台无 warning / error
- [ ] 国际化文案是否补齐（`src/lang/package/`）
- [ ] 权限指令 / 按钮权限是否生效
- [ ] 与 Mock 切真接口时字段是否能对上
- [ ] diff 中没有无关文件改动（package.json、lock 文件、格式化噪音）

## 七、高频反模式（避免）

| 反模式 | 正确做法 |
| --- | --- |
| "帮我把这个项目优化一下" | 拆成具体小任务，逐个说明目标 |
| "你看着办" | 给约束、给参考、给验收标准 |
| 一次性生成 10 个文件直接 Accept | 分步生成，每步 review |
| 报错直接丢一句"报错了你修一下" | 贴完整错误栈 + 复现步骤 + 你已尝试什么 |
| 让 AI 同时改业务 + 重构 + 加测试 | 一次只干一件事 |
| 不看 diff 直接 commit | 必看 diff，至少扫一遍变更文件清单 |
| 让模型猜字段 / 猜接口 | 把字段定义贴出来，或让它先去读 Mock 文件 |

## 八、Agent 模式专属技巧

1. **善用工具调用**：让它跑 `grep_search` / `file_search` 自己找代码，比你描述更准。
2. **任务清单可视化**：复杂任务让它用 todo list 跟踪，自己也能看见进度。
3. **运行命令前确认**：涉及 `pnpm install`、`git push`、删文件，先看它要执行什么再放行。
4. **失败时让它"先分析再重试"**：而不是一直重复同一种错误尝试。
5. **结束时让它自查**：
   > "把本次改动涉及的文件列出来，并简述每个文件做了什么，标出最可能出错的地方。"

## 九、一个完整示例（新增"周末出行"模块）

```
【目标】新增"周末出行"列表 + 详情页
【背景】数据已存在 mock/data/weekend-trips.json，参考 mock/travel.mock.ts
【范围】
  - src/api/travel/weekend.ts（新建）
  - src/views/travel/weekend/index.vue（列表）
  - src/views/travel/weekend/detail.vue（详情）
  - mock/menu.mock.ts（追加菜单）
【约束】
  - 仿照 src/views/affairs/requirements/ 的代码风格
  - 不新增依赖
  - 表格使用项目内 Pagination 组件
  - 详情页用路由参数 :id
【验收】
  - 访问 /travel/weekend 可看到列表
  - 点击行可跳详情
  - 列表支持按"目的地"搜索
  - tsc + eslint 通过

先不要写代码，先告诉我你打算怎么拆步骤、每一步产出什么。
```

> 让模型**先输出计划**，你确认后再让它动手——这是质量最高的协作方式。

## 十、一句话总结

> **"清晰的目标 + 充足的上下文 + 小步验证 + 必看 diff"** ——
> 模型再强，也替代不了你作为工程师的判断和把关。
